# Executor design plan: the best executor for a fixed model

Goal: for each of WebVoyager, AndroidWorld and GameBoyRL, find the best executor design (and, where it helps, the best
supervisor adaptation) for a fixed model. The work runs as a controlled experiment: read prior work, turn it into
features, screen each feature, combine the winners, and confirm the final designs on the full benchmarks.

Related files:
- `plans/executor_lit.md`: the literature review and feature catalogue (step 2).
- `progress.md`: the running log of results and status.
- `plans/decisions.md`: judgement calls.
- `storage/eval/...`: the eval runs.
- `storage/eval/ablation_tables.md`: the earlier supervisor ablation, whose method this plan reuses.

---

## 0. Scope and what is held fixed

**Paradigm:** we keep the supervisor-executor paradigm.
- **The executor** is the per-step policy. Its parts are:
  - **observation:** what it sees and how that is formatted;
  - **action space:** what it can do, and how actions are grounded;
  - **reasoning:** what it writes before acting;
  - **memory:** what it carries between steps;
  - **recovery:** what happens after a bad, invalid or no-op step;
  - **test-time compute:** extra calls per step.
- **The supervisor** sits above the executor. It can also be adapted, by changing prompts, intervention points or what
  it is shown, but it stays a supervisor: we don't collapse it into the executor or invent a new paradigm. The
  baseline arm has the supervisor off (as before).

**Held fixed across all arms:**
- **Model:** `google/gemma-4-31b-it`, served by vLLM. No other model is used for anything (no separate grounding,
  OCR or judge model).
- **Decoding:** the eval harness defaults. A feature may change temperature or sampling only if the feature *is*
  sampling (for example voting).
- **Fine-tuning:** none.
- **Evaluation:** step limits, task sets and scoring are the harness defaults, the same for every arm.
- **Extra model calls:** allowed, but they are costed (§1).

**Envs and tasks:**
- **Web:** WebVoyager through `cusi/eval/web.py`.
- **Android:** AndroidWorld through `cusi/eval/android.py`.
- **GameBoy:** only the GameBoyWorlds benchmark tasks for **Pokémon Red** and **Pokémon Crystal**, through
  `cusi/eval/gameboy.py`.
  - The executor may use the screen, the env's provided info dicts, and our screen text reader
    (`cusi/envs/gameboy_text`, which reads tile maps from VRAM; this is explicitly allowed).
  - **Nothing else is wired from emulator RAM or ROM:** no party, map, coordinate, flag or inventory reads, even
    where it would help.

**Splits:**
- **Dev:** a fixed subset per env, used for screening and combination. It is chosen once, before any feature runs,
  and disjoint from any task used for prompt examples.
- **Test:** the **full benchmark** for each env (full WebVoyager, full AndroidWorld, all Red and Crystal tasks). It is
  run only in step 6. Dev tasks are part of the full benchmark, so the final number is reported both on the full set
  and on the held-out part (full minus dev). This shows how much dev overfitting there is.

**Budget:** there is no fixed compute budget. I keep working and the user checks in. Cost still decides between
designs whose success is similar (§1).

---

## 1. Baseline and measurement

1. **Baselines:** run the current executor for each env (supervisor off) on the dev split with **3 seeds**.
2. **Noise floor:** the seed-to-seed spread and the paired differences between seeds give the smallest effect each
   dev split can detect. This fixes:
   - the dev subset size (grow it if the floor is above about 5 points);
   - when one seed is enough for screening.
3. **Metrics per arm** (in the format of `ablation_tables.md`):
   - success with a 95% CI;
   - the paired difference against baseline (bootstrap and McNemar) and per-task wins and losses;
   - steps, model calls and tokens per task;
   - seconds per task (mean and p90) and GPU-hours;
   - successes per GPU-hour;
   - how episodes end (done, max steps, truncated, error).
4. **Tables:** generated by script from the episode records, never by hand.

## 2. Prior work, then a failure analysis

### 2a. Literature and harnesses

The output is `plans/executor_lit.md`. I search actively, not only from memory: web search, paper reference lists,
and the GitHub repos and READMEs of each harness. Starting points:
- **Web:** WebVoyager (its own harness), SeeAct, Agent-E, WebArena and VisualWebArena baselines,
  Set-of-Mark prompting, AgentOccam, the Browser-Use and OpenHands web agents, tree search for web agents
  (Koh et al.), WILBUR, Agent Workflow Memory.
- **Android:** AndroidWorld's M3A and T3A, Mobile-Agent v1/v2/v3 and Mobile-Agent-E, AppAgent v1/v2, Agent S/S2,
  UI-TARS, Aguvis, OS-Atlas, CogAgent, AutoDroid, DroidBot-GPT, AndroidLab.
- **Games:** the GameBoyRL agents, the Claude Plays Pokémon and Gemini Plays Pokémon harness write-ups, PokéLLMon,
  Voyager, Cradle, BALROG, VideoGameBench.
- **General:** ReAct, Reflexion, Self-Refine, self-consistency and voting, verifier and critic loops, plan-and-execute,
  hierarchical agents, memory designs (MemGPT-style notes, trajectory summaries).

**Read `initial_browse.md` first** (project root; removed 2026-10-19 after the design work). It already surveys AndroidWorld and WebVoyager agents from other
repos, so the search builds on it rather than repeating it. It covers:
- the AndroidWorld agent families: Google's index-based agents, Qwen `mobile_use` coordinate agents, hybrid
  screenshot-plus-layout agents and multi-agent designs;
- WebVoyager's own agent and other WebVoyager agents, with side-by-side feature comparisons;
- why scores aren't comparable across repos;
- known bugs and blockers by repo.

Every feature it describes goes into the catalogue, with source `browse:<repo>` (and the underlying paper or harness
where it names one). Its comparability notes (§4 and §6 there) guide how much weight a reported gain gets.

For each source the file records:
- the idea in one line;
- the reported gain and the setting it was measured in;
- whether it applies to our setup (one fixed model, no extra models, no RAM on GameBoy).

### 2b. Aggregation

The ideas are merged into **features**. One feature is one switch we can flip; the same idea from five papers is one
feature with five sources. The catalogue has a table:

| ID | Feature | Layer (obs / action / reasoning / memory / recovery / compute / supervisor) | Envs | Sources | Failure buckets targeted | Expected cost | Status |
|---|---|---|---|---|---|---|---|

**Source tracking:** every feature has an ID (`F01`, `F02`, ...). The *Sources* column lists where it came from,
using these kinds:
- `paper:<short name, year>`;
- `harness:<repo>`;
- `browse:<repo>`, for features taken from `initial_browse.md`;
- `failures:<bucket>`, for ideas from our own failure analysis;
- `user`, for user suggestions;
- `ours`, for ideas from this repo's state-space work.

Every result row, decision and final design keeps the IDs, so any component can be traced to its origin.

### 2c. Failure taxonomy

I sample about 50 failed baseline dev episodes per env and label each with one main failure bucket. The VLM labels
first, using the same fixed model, and I spot-check about 20% by hand. Expected buckets:
- grounding miss (right intent, wrong element or coordinates);
- wrong plan or misread task;
- finishing too early or claiming false success;
- loop or no-op actions;
- invalid action format;
- running out of steps;
- misreading the screen;
- env or harness error.

Features are ranked by **failure mass addressed × strength of evidence ÷ cost**. That ranking sets the order of
screening.

## 3. Candidate features (seed list; step 2 refines and sources it)

**Observation**
- Set-of-Mark numbered boxes on the screenshot (Web and Android).
- Text alongside the image: `text_boxes` (all three envs; on GameBoy from the screen text reader), the a11y tree,
  pruned DOM text.
- Screenshot resolution and crops.
- The previous frame, or a before/after diff.
- The task and any constraints restated each step.

**Action space**
- Element IDs versus coordinates versus both.
- Composite actions: type then submit; scroll to an element; open an app directly (Android); go back or navigate to a
  URL (Web).
- **GameBoy:** button hold or repeat counts; macro moves ("walk N steps up"); menu macros, built only from screen
  state and info dicts, no RAM.

**Reasoning**
- A ReAct thought before each action.
- Structured JSON output.
- A persistent plan or scratchpad that is updated each step.
- A self-check of the done condition before stopping.
- Asking explicitly "what changed since the last step?"

**Memory**
- A summary of the action history (M3A style) versus the raw recent history.
- A notes buffer for facts found during the task (answers, values).
- **GameBoy:** a visited-places and objectives log, written by the model from what it sees.

**Recovery**
- No-op detection by frame diff, which triggers a reflection.
- Loop detection over recent states.
- Re-prompting on an invalid action, with the parse error.
- Backtracking (Web: go back; Android: back or home).

**Test-time compute**
- Sample k actions and vote (self-consistency).
- Generate and verify: the same model critiques a proposed action before it runs.
- Best-of-k actions with a same-model judge.

**Supervisor adaptations** (inside the paradigm)
- Different intervention triggers: on a stall or loop rather than every N steps.
- What the supervisor sees: a summary versus the full history.
- Supervisor-written plans that the executor tracks.

Each feature has a guess at the failure buckets it addresses. Screening checks that guess (§5).

## 4. Implementation: quick to try, clean for the winners

- **Prototypes:** features under test live in scratch code, such as `tmp_exec_features.py` or a few `tmp_*.py`
  modules. They hook into the executors with as little change as possible: monkeypatching, small wrapper executors,
  and flags read from `--extra`. Nothing needs to be clean; it only needs to be correct and logged.
- **Recording arms:** each arm's config (feature IDs plus parameters) is hashed with `hash_meta_dict` and recorded
  with `write_meta`, so every eval run states exactly what it ran.
- **Sanity check before eval budget:** a 3-to-5-task live smoke run, plus a quick look at the episode records, to
  confirm the feature does what it claims.
- **Clean implementation:** only for the features in a final design, as switches on
  `cusi/agents/executors/base.py` (and the env executors and supervisors as needed), following CLAUDE.md conventions,
  with unit tests. The scratch code is then dropped.

## 5. Experiment stages

1. **Screening (dev, one seed unless the noise floor says otherwise):** each feature alone against baseline on the
   same tasks, compared pair by pair.
   - **Promote** if the paired gain is at least the noise floor and cost rises less than 2×, or if the feature is
     neutral overall but clearly fixes its target failure bucket. Such a feature may combine well.
   - **Drop** if it clearly hurts, or costs much more for no gain.
   - **Retest with more seeds** if it is borderline.
2. **Combination (dev, 2 to 3 seeds):** build the design greedily. Add the promoted features in rank order and keep
   each one only if the combination improves. Then try swapping in the next-best alternatives, to catch
   interactions. Supervisor adaptations are tested on top of the best executor so far.
3. **Leave-one-out (dev, 3 seeds):** remove each component of the best design in turn. A component whose removal
   doesn't hurt is dropped (the simpler design wins ties).

Decision rules are written into `plans/decisions.md` *before* each stage runs. Every run, result and decision is
logged in `progress.md` with its feature IDs.

---

## 6. Final confirmation (full benchmark)

- Run the final design for each env (clean implementation from §4) on the **full benchmark** with **3 seeds**,
  together with the baseline on the same tasks and seeds.
- Report:
  - success with CIs, on the full set and on the held-out part;
  - paired differences against baseline;
  - per-task wins and losses;
  - cost per task and successes per GPU-hour;
  - comparison with the native harness and parity numbers from the earlier eval work.
- The final design for each env is written up with every component's feature ID and sources (§2b).

---

## 7. Interaction with this repo's state-space features (finalisation only)

During **finalisation** (after §5, not during dev screening) I check how the final executors relate to the repo's
state-space machinery:
- `text_boxes`;
- the trigram text and frame/region novelty archive (`cusi/state`);
- VLM-discovered features (`cusi/search/features.py`);
- the tree search and curiosity exploration runs.

Questions to answer:
- **Observation:** does feeding `text_boxes` (already a dev feature) change which state-space keys matter? Is the
  executor's view of a screen the same as the archive's?
- **Recovery:** can the novelty archive, kept *within one episode*, replace an ad-hoc loop or no-op detector (a
  revisited state means a loop, near-zero novelty means a no-op)? This is a same-repo signal, not an extra model.
- **Progress signal for the supervisor:** episode novelty and yield as a trigger for intervening.
- **Prior knowledge from exploration:** can app or game knowledge from our exploration and search runs (discovered
  features, descriptions) be given to the supervisor or executor as context, and is that fair on the full benchmark?
  It must not leak task solutions.
- **Back the other way:** does the final executor suggest better state features for the search (for example the
  features it reads to decide progress)?

Anything adopted from here is screened like a feature (source `ours`) and must not change the dev-chosen design
without its own paired evidence.

---

## 8. Order of work

1. Pick the dev splits; run the baselines with 3 seeds; measure the noise floor.
2. The literature search and `plans/executor_lit.md`, plus the failure taxonomy, at the same time as step 1.
3. Rank the features; prototype and screen them per env, highest ranked first. The three envs run in parallel.
4. Combination, then leave-one-out, per env.
5. Clean implementations of the winners in `base.py` and the env executors.
6. The §7 interaction check.
7. Full-benchmark confirmation with 3 seeds.
8. The final write-up.

Status lives in `progress.md`. This file changes only if the plan itself changes.
